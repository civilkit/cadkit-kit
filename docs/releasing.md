# Releasing

One product version, in one place: `version` in the root `package.json`. The kit app ships the kernel wasm it was built with, so a
release is the pair (kit, kernel). Versions are `MAJOR.MINOR.PATCH`: a new feature or a visible change raises MINOR, a fix PATCH, a
change that stops old files opening MAJOR. The document format has its own number (the `format` and `version` fields of a
`ck-part`), which only changes when files change shape; opening older files stays supported across versions.

## What users can see

- `version.json` next to the live app: `{ "version": "0.5.0", "kit": "<commit>", "kernel": "<kernel build>" }`, written by
  `npm run build:pages`.
- Settings (the gear), at the bottom of the dialog: "Version 0.5.0 (app <commit>, kernel <build>)".
- `CHANGELOG.md`: one section per release, dated, written for users. Add each user-visible change under **Unreleased** in the same
  commit that makes it. A release is exactly what is under Unreleased when you cut it. Write each entry as a bold title and one or two
  short sentences: what a user can now do or what changed. The What's new page shows only the title and the first sentence (about
  200 characters at most), so put the point first; detail belongs in the guide, not the changelog.

## Cutting a release

0. **The go-live gate is in the scripts, not in anyone's memory** (`tools/ci_gate.mjs`). The exact kit commit needs a GREEN full-tier kit CI run (it starts when you `git push ci main`, about 50 minutes; log `ci/logs/kit/` on the box), and the kernel must be the commit in `tools/ci/LAST_GREEN` of its checkout (`tools/ci/full_gate_on_main.sh`) with the wasm that gate wrote. `tools/release.mjs` (tagging) and `tools/deploy_site.mjs` (going live) both look this up and stop when it is not met. There is no bypass flag: red means go back and fix it. **Two modes** (owner's rule, 2026-11-23): an official release (`deploy_site.mjs` with no flag) is always gated; while nobody else uses the app, the owner may ask for a PREVIEW deploy of unverified work to the live site to try it (`deploy_site.mjs --preview`: no gate, `version.json` says `"channel":"preview"`, logged in `_export/hist/DEPLOY_LOG.md`). A preview is never a release: no tag, no public sync, no release post. A targeted `remote_vitest` of one file is NOT a substitute (0.8.7 to 0.8.9 shipped with the kit CI red because only that was checked).
0b. **Two ways to satisfy the kit-CI requirement without a fresh 30 to 50 minute run, both fail closed** (pure rules in `tools/gate_rules.mjs`, tests in `tools/gate_rules.test.ts`; owner-approved 2026-11-25). Anything they do not recognise falls back to the full requirement above.
   - *Release commit on green parent* (automatic in `ci_gate.mjs`): a commit that has no CI verdict of its own may use its parent's GREEN full-tier verdict when its subject is `Release X.Y.Z`, tag `vX.Y.Z` points at it, and `git diff parent..commit` touches only what `release.mjs` writes (the CHANGELOG with just a new `## X.Y.Z - date` heading, the version line alone in `package.json`, `desktop/package.json`, `desktop/src-tauri/Cargo.toml` `[package]` and the `civilkit-cad` entry of `Cargo.lock`, and the generated `apps/cad/public/whats-new/index.html`, which must equal, byte for byte, what `tools/make_whats_new.mjs` writes from that commit's own CHANGELOG and highlights: the gate regenerates it in a temporary extract of the commit, `tools/gate_regen.mjs`). Safe because the tests would run on the same code; a RED or FLAKY verdict on the commit itself is never overridden, and a missing, RED or FLAKY parent refuses. The kernel check is unchanged. The gate prints `Release commit on green parent <sha>` when it used this.
   - *Content-only deploy* (`deploy_site.mjs --content-only`): skips the kit-CI requirement, and only that, when the live `version.json` is a `release` channel build whose kit commit is an ancestor of HEAD, the diff live..HEAD is only What's new content and prose (`apps/cad/public/whats-new/**` images and page, `docs/whats-new/**`, `CHANGELOG.md`, `tools/clips/**`, `docs/**/*.md`; the page is regenerated and compared byte for byte, posters must really be images by their magic bytes, no `.html` other than the page, no svg/js/css/wasm, no symlinks or mode changes, and committed `.mp4`/`.webm` are refused because clips are not committed), every untracked or ignored file the build would copy from `apps/cad/public` is a clip (`.mp4`/`.webm`) or a poster image in `whats-new/clips` or `whats-new/posters` (anything else untracked refuses and is listed), the kernel checkout and the wasm's full-gate folder are the live kernel, the tree is clean and on `main`. Safe because the app code and kernel that were gated are byte-for-byte what ships. Clips are added to a content-only deploy by copying them untracked into `apps/cad/public/whats-new/clips/`. It builds, smokes and deploys on the release channel and logs `content-only over <live sha>`. `--dry-run` says which mode applies and why it refuses.
1. Check kit `main` is what you want to ship, with the kernel wasm you intend to publish (the one that passed its gate). Run the kit's tests against the kernel checkout you ship: the kit resolves the kernel's TypeScript packages (`@ck/*`) from `../rebuild`, which other sessions leave on any branch, so a stale one fails tests that are not broken (`sheetHints`, the skill `registry` test). Use `CK_REBUILD=<kernel checkout> npx vitest run`, or fast-forward `../rebuild` to the kernel main first.
1b. Rename the `Unreleased` key in `docs/whats-new/highlights.json` to the new version (commit it) BEFORE running the release script: the script does not do it, and a page generated without it shows the release with no highlights (this happened with 0.6.3 and needed a re-tag). Give the kernel tag a `--kernel-ref <hash>` of the commit the gated wasm was built from, since kernel main may have moved on.
2. `node tools/release.mjs minor --dry-run` shows the version, the number of entries and the notes it would write.
3. `node tools/release.mjs minor --kernel-repo /path/to/kernel-checkout` (or `patch`, `major`, or an explicit `X.Y.Z`):
   runs the i18n check and `npm audit --omit=dev --audit-level=high` (a high or critical advisory in what ships stops the release; it needs the network, `--no-checks` skips both), moves Unreleased under `## X.Y.Z - date`, bumps `package.json`, commits `Release X.Y.Z`, tags `vX.Y.Z`
   (the tag message holds the notes) and tags the kernel checkout's HEAD with the same `vX.Y.Z`. Nothing is pushed or deployed.
4. Push the tags to `ci` and wait for the kit CI to go green on that commit. Then `node tools/deploy_site.mjs --kernel-repo <kernel checkout> --wasm <ck-full-gate>/<time>-<sha10>/ck_wasm.wasm`: it checks the gate, builds the pages, smoke-tests them, deploys to Cloudflare Pages and waits until `https://civilkit.io/cad/version.json` shows this kit commit. It is the only way to deploy; do not run `wrangler pages deploy` by hand.
5. (Done by `deploy_site.mjs`; check its last line says LIVE.)
6. Build the Mac app for the same release (every release ships it): from the tagged checkout run `WASM_SRC=<the same wasm> CK_REBUILD=<kernel> tools/desktop_build.sh` (see `docs/desktop.md`), the build also compiles the native kernel from `CK_REBUILD` and checks the kernel commit is inside each `.app` (if you build with `tauri build` by hand, set `CK_COMMIT` and point `ck-native` in `desktop/src-tauri/Cargo.toml` at the same kernel checkout, then check the `.app`'s Settings > About shows the native kernel), check the `.dmg` and the `.app.zip` names carry the version, and add the arm64 and x64 files and `SHA256SUMS` to a draft GitHub release tagged `vX.Y.Z` (the same tag as the public sync; from 0.7.1 on, earlier ones used `desktop-vX.Y.Z`). Publishing the draft is a separate step for the owner.
7. Draft the r/civilkit post: `node tools/release_post.mjs X.Y.Z --out <dir>` (add `--mac` once the draft GitHub release of step 6 is published, and `--catchup <from>` for one post covering several versions), read it, and hand the text to the owner to post. The owner is the only moderator; never post it automatically.

## What's new clips

**Four clips per release.** A release is meant to carry four visual changes, each with a short clip and a poster (owner, 2026-11-25). `tools/release.mjs` counts the highlights of the new version in `docs/whats-new/highlights.json` that have `clips/<id>.mp4`, `clips/<id>.webm` and `posters/<id>.png`; with fewer than four a dry run warns and a real run refuses, unless you pass `--clips-ok "<why>"` (the reason is printed and kept in the Release commit body). Clips are not committed, so run the release from the checkout that holds them. A content-only deploy (`deploy_site.mjs --content-only`) can add clips later without a full CI.

Each highlight in `docs/whats-new/highlights.json` can have a short looping clip. `node tools/clips/record.mjs --dir dist-pages-civilkit/cad --profile <scratch dir> [--only <id>]` records the clips of `tools/clips/NN-name.mjs` against a built pages app (headless Chrome at a device pixel ratio of 2, so retina: CDP screencast, ffmpeg with VP9 and H.264, 1920 px wide, at most 4 MB each; the encode of one clip takes a few minutes). The clip files (`apps/cad/public/whats-new/clips/`) are not committed: the build copies them into the deploy. The posters (`posters/<id>.png`, at most 120 KB) are committed. List clips made ahead of a release under the key "Unreleased" and rename the key when you cut the release. Look at every clip before it ships.

## Keeping the guide current

The guide (`guide/`, published at `/docs/cad/`) is checked at release time: build it (`mdbook build guide`) and read the Unreleased
entries against it. For each entry that adds or changes something a user does, the guide has a page or a paragraph, or the entry says
why not. Generated references (the script API from `registry.generated.json`, the command lists) are regenerated, never hand edited.

## Site chrome

Every static page of the suite (home, Calcs, CAD What's new, licences, the /docs/ index, the guides) uses one stylesheet, `https://civilkit.io/styles.css`,
and the same header and footer. The civilkit-site repo owns the stylesheet and the markup. This repo carries a copy of the header and footer in
`tools/pages/siteChrome.mjs` (used by `tools/make_whats_new.mjs`, the licences page and the /docs/ index), and the Calcs repo carries another. Change
the navigation in all three together, and deploy civilkit-site first: the pages here rely on the components it adds to `styles.css`. The guide
(`guide/civilkit.css`) and the kernel book use the same palette through an mdBook stylesheet override instead of the header.
